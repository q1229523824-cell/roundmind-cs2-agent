# 全结果交火决策比较

死亡样本只能告诉系统哪里失败，不能回答“同样条件下成功或主动脱离时，判断标准是否一致”。
`contact_decision_scoring.py` 因此对 `kill`、`death`、`disengaged` 三类交火使用同一套事前评分。

## 防止结果泄漏

评分只读取交火开始时或第一段伤害发生时可观测的条件：

- 谁先造成第一段伤害；
- 接触前血量；
- 最近队友距离与补枪准备代理；
- 接触瞬间的准星方向；
- 是否仍有存活队友。

最终结果、最终造成/承受伤害、交火持续时间和结束 Tick 只用于赛后校验，不参与风险分、候选动作风险或
推荐动作。测试会把完全相同的事前条件分别改成击杀、死亡与脱离，并要求三张卡的评分和动作完全一致。

## 候选动作

每张卡至少比较两个、最多四个动作：

1. 继续当前接触；
2. 脱离并重置枪线；
3. 存在存活队友时等待支援条件；
4. 先创造烟、闪或燃烧弹条件。

“等待支援”假设队友能进入同一交火窗口；“创造道具条件”假设玩家或队友仍有合适道具和施放时间。
当前 Demo 没有在 `ContactEpisode` 中保存完整库存，因此这些假设会随候选动作一并输出，不能伪装成事实。

## 输出边界

底层会评分全部交火，但单场 API 默认只返回 12 张代表卡：优先保留三类结果各最多两张，再按事前风险
补齐。这样不会让死亡样本淹没成功与脱离对照，也不会把 100 多次交火全部塞进大模型上下文。

当前分数是可解释规则基线，不是真实胜率预测。下一步应由人工盲标“当时更合理的动作”，评估推荐动作
一致率，并用更多地图和版本数据校准阈值，而不是根据最终输赢反向调分。
