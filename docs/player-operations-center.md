# 玩家运营中心与质量观测

这一阶段把 RoundMind 从“单次上传后生成报告”扩展为可持续使用的训练产品，包含任务指标、Demo 数据质量、历史比赛、玩家画像和可选登录五部分。

## 页面数据流

```text
浏览器
  ├─ 上传 Demo ──> Demo 任务 ──> 解析 ──> 比赛报告
  │                                └─> 数据质量门禁
  ├─ 历史比赛 ──> 当前用户拥有的比赛摘要
  ├─ 玩家画像 ──> 同一 SteamID 的多场聚合
  └─ 登录令牌 ──> Authorization: Bearer <JWT>
```

前端只把 JWT 保存在当前浏览器标签页的 `sessionStorage`，关闭标签页后不会长期保留。后端开启强制鉴权后，比赛、Demo 任务、画像和教练对话都通过用户 UUID 隔离；未开启时，页面明确显示“匿名体验模式”。

## 新增接口

- `GET /api/system/job-metrics`：返回保留任务数、等待任务数、各状态数量、成功率和平均耗时。
- `GET /api/system/parser-accuracy`：返回匿名 verified Demo 解析准确率；没有人工真值时明确显示等待状态。
- `GET /api/match-history`：返回最近 50 场轻量比赛摘要和质量分。
- `GET /api/matches/{match_id}/quality`：返回指定比赛的数据质量门禁结果。
- `GET /api/quality-summary`：返回当前可见比赛的批量质量汇总。
- `GET /api/player-profiles/{steamid}`：聚合同一玩家的跨场角色和习惯画像。

## 质量门禁的意义

质量分不是玩家水平分，而是“本场解析数据是否足以支持建议”的可信度分。门禁会检查回合、击杀、死亡、经济和关键事件是否完整：

- `pass`：可用于长期画像和训练建议；
- `review`：可以展示，但建议降低结论置信度并人工复核；
- `fail`：不应写入长期画像，避免把解析缺失误判成玩家习惯。

## 正式启用登录

生产环境需要先提供 PostgreSQL，再设置：

```text
DATABASE_URL=<PostgreSQL 连接地址>
ROUNDMIND_JWT_SECRET=<至少 32 字符的随机密钥>
ROUNDMIND_AUTH_REQUIRED=true
```

不要把这些值写进代码或提交到 Git。修改 Render 环境变量后重新部署，前端会通过 `/health` 自动发现鉴权已经启用并显示登录/注册表单。

## 当前观测边界

内存任务管理器的指标只代表当前后端实例，并会在进程重启后清零。启用 Redis/Celery 后，应把跨实例任务计数和耗时汇总接入统一指标系统。历史比赛和用户隔离依赖 PostgreSQL；未配置数据库时仅适合本地学习和匿名演示。

## 面试可讲的设计点

- 用异步任务状态机处理 500 MB Demo，前端展示进度、取消和失败恢复。
- 在业务建议前设置数据质量门禁，防止“错误数据生成看似合理建议”。
- 用 JWT 和 Repository 所有权过滤实现数据隔离，接口不存在与无权限统一返回 404，减少资源枚举风险。
- 将单场报告、历史比赛和跨场画像分层，避免把偶然表现直接当作长期习惯。
- 用成功率和平均耗时观察任务管线，同时明确单实例指标的适用边界。
